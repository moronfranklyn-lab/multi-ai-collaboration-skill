# 活文档与发布

用于有持续维护价值、需要多个实例读取的正式交付物。临时讨论、一次性草稿与本地实验沿用轻量交接，不强制登记，不与正式成果争夺“当前版本”。

## 固定入口与目录

同一个正式交付物只有一个当前维护入口，原位更新；不按版本另建一串“最新版”文档。目录按具体交付物登记，不把不同项目所有工程方案混成一份文件。

目录最少包含：交付物名称、类型、固定链接、当前版本、状态、责任人、最后修改、上一版本。可沿用现有表格或维护清单，不要求新开数据库。通用条目见 [目录模板](../templates/deliverable-record.json)。目录只保存索引和版本，审计保存在独立追加台账，正文保存在原位置。

新正式交付物先在目录登记为草案或待合并，再在核验发布成功后标为生效。未经登记的产物仍可作为草稿交流，不能冒充已发布成果。已有交付物先查目录复用入口，不先建副本再要求负责人删除旧版。

文档标题保持稳定，不写版本号；历史优先使用平台 revision 或 Git commit。确需保存恢复快照时，放入受控历史位置并明确标为非当前版本。迁移或固定链接失效时，须按授权调整目录并记录旧新入口关系，不静默切换。

## 状态头与格式映射

人工阅读的正式文档在正文第一行写：

```text
状态｜版本｜最后修改时间｜修改人｜基于版本｜依据
```

六项均须有真实值。首次创建的基于版本可写“无”；不知道则写 UNKNOWN，并保持草案或待核实。只有状态为生效、必要信息完整且发布有依据时，才能被下游当作当前正式版本。头部填满不代替结果核验和用户授权。

模板首行使用草案和 UNKNOWN，不得直接复制模板就宣布生效。更新时间使用明确日期，涉及跨时区协作时带时区；平台自动时间不一定代表业务事件时间。

机器格式采用等价元数据：Skill 保留 YAML frontmatter 并用 metadata.version；代码或包使用现有 manifest、Git ref/commit 与批准记录。目录记录与实际元数据、版本引用相互对应，缺失的负责人、依据等可指向受控发布记录。不在 YAML、JSON 或代码前插入自然语言状态头。仓库固定入口表示发现入口，具体成果版本用 commit 或发布引用核验，不能把可变分支名当作不可变版本。

正式发布的版本号须关联可核验内容，不静默改绑为不同内容或 commit。后续内容变更使用新版本，或按项目规则追加明确的更正关系，保留原版本定位。

## 读取当前成果

读取顺序为“目录 → 固定链接 → 状态头或原生元数据”。先看目录状态与责任人，再核对正文实际版本和平台 revision，最后按任务读取相关差异与证据。

目录决定应访问的正式入口和期望版本；若目录写 v2、正文仍是 v1，不能把旧正文称作 v2，也不能自行认定正文更晚就已生效。报告两端实际状态与定位，暂停依赖该版本正确性的发布或业务修改；不受影响的分析可继续。由责任人核实并补齐缺失发布步骤，不通过创建另一个“当前文档”解决。

## 按责任更新与留痕

1. 确认自己是该交付物责任人或获准临时代理，且本次修改在授权范围。非责任人的建议以待合并稿交付。拥有某文档权限不等于拥有所有交付物或业务事实的维护权。
2. 责任人修改前重读正文、目录版本和 revision，保留前版本；存在并发时使用版本条件、锁或串行提交。整篇 overwrite 仅由责任人或明确指定的代理执行；跨责任人修改交由责任人合并。
3. 在固定位置更新内容及六项状态头或原生元数据，保留他人修改。规划结构、范围、依赖或验收改变时，沿用项目约定的提案与批准流程，不因可自行发布而扩大决策权。
4. 核验实际成果，更新目录的当前版本、最后修改、上一版本与实际状态，必要时更新责任人。不能只改目录版本而不修改、核验正文。
5. 实际执行者直接追加事件，写明改了什么、为什么、基于哪个版本、现在是哪个版本、差异在哪里。其他实例接手时按目录和差异获取上下文，无须让事实维护者重新通读后代记。

正文、目录和台账通常不在一个事务内。分别跟踪成功项：正文成功、目录失败时，不重写正文；保留已知 revision，报告目录待补，恢复后核对再更新目录。目录已成功、审计失败时，只补审计。任何状态不明先查实际结果，不盲目重试。补记有明确责任人和触发方式，完成前不报告发布闭环。

恢复时重读正文、目录及后续事件；若已出现更新的有效版本，按当前状态补齐缺口，不能把旧待补版本机械写回目录。有人已完成修复时核验并关联事件，不重复修复。

各实例能看到同一入口是访问能力，是否实际读取是执行行为。除非已经配置并验证同步或通知机制，否则不声称其他 AI 自动知晓更新，也不擅自发消息或创建后台任务。
